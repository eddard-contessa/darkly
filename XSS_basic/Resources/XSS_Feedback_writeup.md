# Darkly — XSS (basic) — Feedback page

## Расположение уязвимости

Страница `?page=feedback` (форма "Sign Guestbook") — два поля:
- `txtName` (Name), `maxlength="10"`
- `mtxtMessage` (Message), `maxlength="50"`

Обе записи сохраняются на сервере и отображаются всем посетителям страницы
(классический guestbook) — это делает уязвимость **persistent / stored XSS**,
а не отражённой: один раз внедрённый payload выполняется у **каждого**, кто
откроет страницу, а не только у автора запроса.

## Механизм уязвимости

Поле **`txtName` не проходит никакой серверной санитизации** — значение,
отправленное в POST-запросе, вставляется в HTML ответа буквально, без
экранирования спецсимволов (`<`, `>`, `'`, `"`).

Поле **`mtxtMessage`, для сравнения, фильтруется** функцией, поведение
которой идентично PHP `strip_tags()` без второго аргумента (без allowed-list):
вырезается любая последовательность от `<` до ближайшей `>` целиком, текст
между открывающим и закрывающим тегом (если он есть отдельно от тега)
сохраняется. Экспериментально подтверждено (см. `XSS_Feedback_explained.md`
для полного протокола тестов):
- `<script>текст</script>` → оба тега вырезаны, `текст` остаётся;
- самозакрывающиеся теги (`<svg onload=...>`, `<img ... onerror=...>`) —
  вырезаются целиком, без остатка;
- незакрытые теги — вырезаются вместе со всем "хвостом" строки, где
  предполагаемая функция ищет несуществующую закрывающую `>`;
- у фильтра нет allowed-list (`<b>` тоже полностью вырезается) — обход
  через "разрешённый" тег с добавленным `on*`-атрибутом невозможен.

**`Message` полноценно защищён от XSS** в рамках выполненных тестов;
уязвимость целиком локализована в поле `Name`.

## Ход эксплуатации

1. Через DevTools увеличен атрибут `maxlength` поля Name (родное
   ограничение — 10 символов, чисто фронтенд, ничего не проверяет на
   сервере).
2. Подтверждено исполнение произвольного HTML/JS в поле Name:
   `<svg onload=alert(1)>`, `<Script>alert(42)</Script>` и другие —
   payload'ы отражаются в HTML один в один и выполняются браузером у
   каждого, кто открывает страницу (persistent XSS подтверждён).
3. Прямой проверкой через `curl` (без браузера, минуя фронтенд-валидацию
   и autofill) подтверждено, что фильтрация/её отсутствие — это серверное
   поведение, а не JS-валидация на клиенте.
4. Экспериментально установлено, что **флаг на этой странице выводится не
   по факту реального исполнения JS**, а по отдельной серверной проверке:
   если отправленное значение `Name` содержит подстроку `script` (без
   тегов, простым текстом) — сервер печатает флаг прямо в HTML-ответ.
   Это отдельный, чисто текстовый детектор успешной эксплуатации, а не
   доказательство именно исполнения кода — но именно наличие полностью
   нефильтрованного поля и делает такую детекцию осмысленной, поскольку то
   же самое поле реально исполняет присланный HTML/JS.

## Результат — флаг

```
0fbb54bbf7d099713ca4be297e1bc7da0173d8b3c21c1811b916a3a86652724e
```

Флаг получен отправкой POST-запроса на `?page=feedback` со значением
`txtName=script` (Message — любое непустое значение, форма требует оба
поля заполненными).

## Сравнение флагов

Флаг, полученный вживую через эксплуатацию (см. выше), полностью совпадает
с флагом, сохранённым в файле `{Breach name}/flag` в репозитории —
идентичность подтверждается побайтовым сравнением на защите (`cat flag`).

## Способ защиты (fix)

- Экранировать пользовательский ввод при выводе: `htmlspecialchars($txtName, ENT_QUOTES, 'UTF-8')`
  вместо вывода как есть.
- Не полагаться на "чёрный список" (`strip_tags()`/поиск подстрок) как на
  единственную защиту — правильный подход: **контекстное экранирование
  вывода**, а не попытка вычистить вход.
- Ограничение длины поля (`maxlength`) должно проверяться и на сервере,
  а не только в HTML-атрибуте — на клиенте оно тривиально снимается.

## Потенциальный ущерб (impact)

Поскольку это persistent XSS, злоумышленник может внедрить payload один
раз, и он будет исполняться у **всех** последующих посетителей страницы,
включая администраторов сайта. Реалистичные сценарии атаки:
- кража cookie сессии (`document.cookie`) и последующий session hijacking;
- принудительные действия от имени жертвы на сайте (CSRF-подобные цепочки,
  инициированные через XSS);
- фишинг/дефейс страницы для всех посетителей одновременно;
- в связке с другими уязвимостями сайта (например, эскалация через cookie
  `I_am_admin`, уже найденную на этапе Cookies) — потенциальный вектор для
  более серьёзной компрометации.
