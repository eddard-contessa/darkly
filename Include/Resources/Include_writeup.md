# Include — Writeup

## Флаг

```
b12c4b2cb8094750ae121a676269aa9e2872d07c06e429d25a63196ec1c8c1d0
```

Получен по адресу:

```
http://<IP>/?page=../../../../../../etc/passwd
```

## Механизм уязвимости (кратко)

Движок сайта строит содержимое страницы через параметр `page` в URL
(`index.php?page=...`). На сервере это значение подставляется без
санитизации в функцию подгрузки файла — судя по поведению сервера,
что-то вида:

```php
include("pages/" . $_GET['page'] . ".php");
```

Так как значение параметра не проверяется и не ограничивается набором
разрешённых имён (whitelist), в него можно подставить путь с
последовательностями `../` ("подняться" из папки `pages/` вверх по
дереву каталогов) и указать абсолютный путь к системному файлу.
Итог — **Local File Inclusion (LFI)**: сервер подключает и выводит
произвольный файл файловой системы, к которому у него есть права на
чтение.

### Как это было найдено (шаги)

1. `?page=doesnotexist123` — несуществующая "страница" → сервер вернул
   отладочное сообщение `Wtf?`. Это подсказало, что параметр `page`
   действительно обрабатывается динамически и реакция сервера меняется
   в зависимости от того, что ему передали.
2. `?page=../../../etc/passwd` (недостаточная глубина `../`) →
   `Still nope..` — сервер явно "понимает", что путь неверный, но
   как-то иначе, чем на просто несуществующей странице.
3. `?page=../../../../etc/passwd` (промежуточная глубина) → `Almost.`
   — прямое подтверждение, что мы близко: не хватает ровно одного-двух
   уровней `../`, чтобы дойти до корня файловой системы.
4. `?page=../../../../../../etc/passwd` (полная глубина) → сервер
   выводит содержимое `/etc/passwd` и печатает флаг:
   `Congratulaton!! The flag is: b12c4b2c...`

Каждый шаг давал явно отличающийся ответ сервера — это и есть признак
того, что параметр обрабатывается как часть пути к файлу на диске, а
не просто как текстовая метка для сравнения со списком разрешённых
страниц.

## Способ защиты (fix)

Наиболее надёжный вариант — **не строить путь к файлу напрямую из
пользовательского ввода**. Варианты, от лучшего к приемлемому:

1. **Whitelist разрешённых значений.** Завести на сервере фиксированный
   список допустимых значений `page` (`home`, `member`, `survey`, ...)
   и просто отклонять (или подставлять значение по умолчанию) любое
   значение вне этого списка:
   ```php
   $allowed = ['home', 'member', 'survey', 'upload', ...];
   $page = in_array($_GET['page'], $allowed) ? $_GET['page'] : 'home';
   include("pages/" . $page . ".php");
   ```
2. Если whitelist по какой-то причине невозможен — минимум убрать из
   ввода символы обхода пути (`.`, `/`, `\`) через `basename()` и
   явно проверять, что итоговый путь остаётся внутри разрешённой
   директории (`realpath()` + проверка префикса).
3. Никогда не давать `include()`/`require()` напрямую читать
   абсолютные пути или пути с `../`, полученные из `$_GET`/`$_POST`.

## Impact (какой ущерб это может нанести в реальности)

- **Утечка чувствительной информации с сервера**: `/etc/passwd`,
  конфигурационные файлы приложения (пароли к БД, ключи API),
  логи, исходный код PHP-файлов сайта — всё, к чему у веб-сервера
  есть права на чтение.
- Если на сервере есть файлы, куда атакующий может записать
  контролируемое содержимое (например, загруженный файл, лог-файл с
  контролируемыми записями — см. этап File upload), LFI может
  перерасти в **удалённое исполнение кода (RCE)**: включить через
  `include()` файл, содержащий PHP-код атакующего.
- Раскрытие структуры файловой системы сервера облегчает дальнейшую
  разведку и подготовку других атак.
