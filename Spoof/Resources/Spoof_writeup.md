# Spoof (curl) — Writeup

## Флаг

```
df2eb4ba34ed059a1e3e89ff4dfc13445f104a1a52295214def1c4fb1693a5c3
```

Получен со страницы `?page=spoof` при подмене cookie `I_am_admin` через заголовок `Cookie` в curl-запросе, без использования браузера и без прохождения формы логина.

## Механизм уязвимости

Страница `?page=spoof` определяет, показывать ли администраторский контент
(флаг), исключительно по значению cookie `I_am_admin`, которое отправляет
клиент:

- Cookie отсутствует, или равен MD5("false") = `68934a3e9455fa72420237eb05902327`
  → сервер отдаёт `alert('Wtf ?')`, флага нет.
- Cookie равен MD5("true") = `b326b5062b2f0e69046810717534cb09`
  → сервер добавляет перед этим ещё один `alert()` с текстом флага.

Сервер **не хранит серверную сессию** и **не подписывает** значение cookie
(нет HMAC/токена, привязанного к секретному ключу на сервере). Он просто
берёт значение, присланное клиентом в заголовке `Cookie`, хэширует его
логику проверки на MD5("true")/MD5("false") и доверяет результату целиком.
Поскольку HTTP-заголовки, включая `Cookie`, полностью формируются
клиентом, значение можно свободно подставить в обход браузера — например,
через `curl -H "Cookie: ..."`, минуя весь пользовательский интерфейс сайта
и процесс логина.

Технически это тот же паттерн уязвимости, что уже был найден и
эксплуатирован на отдельном этапе **Cookies**: там cookie редактировался
через DevTools в браузере. Здесь этот же принцип демонстрируется на
примере эксплуатации **без браузера вообще**, чисто через HTTP-клиент
(curl) — отсюда и название этапа "Spoof (curl)": подделка идентичности/прав
клиента произвольным HTTP-инструментом.

### Важное уточнение по ходу расследования

На странице `?page=survey` в HTML-комментариях были найдены две подсказки:

```html
<!-- You must come from : "https://www.nsa.gov/". -->
<!-- Let's use this browser : "ft_bornToSec". It will help you a lot. -->
```

Они наводят на мысль, что для доступа нужно подделать заголовки `Referer`
и `User-Agent`. Эта гипотеза была явно проверена экспериментально:

| Cookie | Referer | User-Agent | Результат |
|---|---|---|---|
| отсутствует | отсутствует | по умолчанию (curl) | `Wtf ?` |
| отсутствует | `https://www.nsa.gov/` | `ft_bornToSec` | `Wtf ?` |
| `MD5("false")` | `https://www.nsa.gov/` | `ft_bornToSec` | `Wtf ?` |
| `MD5("true")` | отсутствует | по умолчанию (curl) | **Флаг** |

Заголовки Referer/User-Agent не влияют на результат ни в одной комбинации.
Единственная переменная, определяющая результат — cookie `I_am_admin`.
Вывод: подсказка на странице survey не относится к этому этапу (см. пункт
"Подсказки для других этапов" ниже) — это осознанно проверено, а не
предположение.

## Демонстрация — сравнение флагов

**Способ 1 — через браузер:**
1. У аккаунта уже был установлен cookie `I_am_admin=b326b5062b2f0e69046810717534cb09`
   (MD5("true")), выставленный ранее на этапе Cookies через DevTools →
   Application → Cookies.
2. Обычный переход браузером на `http://127.0.0.1:8080/?page=spoof`
   автоматически отправляет этот cookie на сервер.
3. Сервер вернул `alert('Good job! Flag : df2eb4ba34ed...')`.

**Способ 2 — через curl (без браузера, без логина):**
```bash
curl -i -H "Cookie: I_am_admin=b326b5062b2f0e69046810717534cb09" \
  "http://127.0.0.1:8080/?page=spoof"
```
В теле ответа:
```html
<script>alert('Good job! Flag : df2eb4ba34ed059a1e3e89ff4dfc13445f104a1a52295214def1c4fb1693a5c3');</script>
```

Оба способа дают **идентичный флаг** — `df2eb4ba34ed059a1e3e89ff4dfc13445f104a1a52295214def1c4fb1693a5c3`,
что подтверждает: способ 2 (curl, без легитимного прохождения сайта)
воспроизводит то же самое состояние "администратора", что и легитимный
путь через браузер.

## Метод, который мог бы предотвратить эту уязвимость

- Не хранить признак прав доступа (роль, флаг администратора) в открытом
  виде на стороне клиента.
- Использовать server-side сессии (например, PHP `$_SESSION`), где после
  успешной аутентификации сервер сам создаёт запись о правах пользователя,
  доступную только на сервере — клиенту выдаётся лишь непредсказуемый
  session ID.
- Если состояние всё же нужно хранить на клиенте (например, в JWT), оно
  должно быть криптографически подписано секретным ключом сервера
  (HMAC/JWT signature), а сервер обязан проверять подпись при каждом
  запросе — попытка подделать значение без знания ключа должна приводить
  к ошибке валидации подписи.
- Дополнительно: не хэшировать простыми/предсказуемыми алгоритмами
  (MD5 от строки "true"/"false") значения, отвечающие за права доступа —
  такие хэши легко подобрать или найти в открытых базах (rainbow tables).

## Выгода / impact атаки

Уязвимость позволяет любому внешнему клиенту получить права
"администратора" сайта без пароля, без прохождения формы логина и без
браузера — достаточно знать (или подобрать) правильное значение cookie.
В реальной системе такой недостаток эквивалентен полному обходу
аутентификации: злоумышленник получает доступ к административной
функциональности, потенциально включающей просмотр/изменение данных
других пользователей, конфигурации системы и т.п. — то есть полный
компромисс приложения без единой попытки подбора пароля.
